# External full-payment tracking

TaskBridge records a payment made outside the platform; it does not initiate transfers, integrate a gateway, verify a bank transaction or hold money. One immutable Client report records the full agreed assignment amount in LKR. There is no installment balance, editable payment history, correction, refund or dispute workflow in this step. Do not enter a report until its full amount and details are correct.

No payment report means Pending. A report means Paid — reported by the Client. Receipt awaiting acknowledgment and receipt acknowledged by the assigned Freelancer are separate states derived from the acknowledgment record; a Client report alone does not acknowledge receipt. Work completion never reports or acknowledges payment automatically, and neither payment action modifies work status, completion metadata, assignment terms, proposals, tasks or deliverable reviews.

Dedicated participant policies allow the owning Client and assigned Freelancer to read the private payment page throughout assignment history, including completed projects. Admins and unrelated users receive no implicit access. Only the persisted owning Client can create a report, for an assigned project in progress or completed. Only the persisted assigned Freelancer can acknowledge an existing, correctly scoped report, including during historical access. GET requests and refreshes are read-only.

The report copies the saved agreed budget after decimal-safe precision/range validation, always sets LKR, and resolves reporter, assignment, UTC reporting time and retry identity on the server. The paid-on date is a calendar date between the assignment's Sri Lankan calendar date and today in Asia/Colombo, inclusive. It can be after the agreed work deadline. Methods are bank transfer, cash or other; the optional reference and plain-text note are trimmed and bounded to 150 and 2,000 characters. The separate acknowledgment resolves its Freelancer and UTC time on the server and permits an optional trimmed 2,000-character plain-text note. User text is escaped when displayed.

Both actions require explicit confirmation and lock the persisted account, project and assignment in the existing order, then the scoped report and acknowledgment. A report is unique per assignment and has a globally unique, protected server-generated UUID (normalized to lowercase). An exact report retry requires the original actor, UUID and normalized method/date/reference/note. A different UUID or changed details are a conflict, even if an assignment already has a report. An acknowledgment retry must have the same actor and normalized note. Exact retries return original timestamps and never rewrite history; known uniqueness conflicts are re-resolved under authorization and locks. Unrelated database failures propagate. A missing competing result is not treated as success.

Restrictive foreign keys and immutable model events preserve reports and acknowledgments. Both are guarded from ordinary mass assignment. Account deletion checks payment-history references before any profile/avatar cleanup, including historical reporters/acknowledgers who no longer own the project. Existing completed-work guards are unchanged.

SQLite in-memory and fake-storage tests cover persisted validation, exact retries, injected uniqueness conflicts, rollback and sequential competing-write simulations. They do not establish real parallel MySQL behavior. Browser/device/theme/keyboard checks and isolated parallel MySQL testing remain deferred in `docs/manual-review.md`; never use development records for concurrency testing.
