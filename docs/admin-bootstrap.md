# First-Admin bootstrap

Run `php artisan taskbridge:bootstrap-admin` only from a trusted interactive terminal after migrations and a database-identity check. The command accepts no account/password arguments or options. `--no-interaction` and non-terminal input fail before querying accounts or prompting. Hidden password input has **no visible fallback**; an unsupported terminal fails safely. There is no web route or dependency/schema addition.

The command trims the name, lowercases/trims the email, validates a meaningful name without terminal control characters (maximum 255), a valid unique email (maximum 255, including case-insensitive historical matches), and confirmed password. The password requires 12 characters, upper/lowercase letters, numbers and symbols, with a 72-byte maximum for bcrypt. It uses local validation, not an external password-checking service. Name/email/role and optional verification state appear before an explicit default-No confirmation. Passwords/hashes and exception payloads are never printed or logged by bootstrap.

Any existing Admin blocks both the prompt flow and the transactional action, regardless of availability. An existing Client/Freelancer email is refused; bootstrap never promotes, edits, replaces or deletes anyone. A new User gets Admin role, an explicitly hashed password, no verification time, no avatar/remember token/suspension, and access version zero, all assigned server-side. No Registered event, external email, audit actor fabrication or project record is produced. The operator signs in normally; verification stays optional and existing session/suspension protection applies.

## Serialization and transactions

`BootstrapAdminCommand` owns terminal interaction; `BootstrapAdmin` owns validation and persistence. On MySQL, a connection-scoped `GET_LOCK` key derived from the configured database name serializes cooperating bootstrap attempts, including an empty users table. It waits at most ten seconds for that lock, then starts its own transaction and reloads the Admin condition with a locking read. It holds the advisory lock through actual commit/rollback and releases it in `finally`; connection closure also releases MySQL advisory locks. Nested MySQL transactions are refused so the mutex cannot be released before an enclosing commit. Configure all operators against the same canonical database identity. Database connection failures and unrelated errors are not treated as successful creation.

On SQLite, a no-op UPDATE acquires the transaction's writer reservation **before** checking for any Admin. MySQL and SQLite are the supported drivers; other drivers fail closed. No row-lock-only empty-set check, cache/file mutex, new unique role constraint or migration is used. Existing multiple-Admin data and last-active-Admin deletion safeguards are unchanged. Direct privileged SQL is outside these application guarantees and must not be used to rewrite account history.

Console validation happens before confirmation, then the action revalidates inside the transaction. Duplicate email races remain protected by the existing database unique key. Creation failure rolls back the inserted account. If another attempt won, the loser reports the existing-Admin condition rather than replacing it. After a timeout/failure, inspect the result through normal authorized operations; rerunning safely refuses any committed first Admin.

## Automated evidence and limits

`BootstrapAdminTest` uses SQLite `:memory:` for successful prompts, hashing, login/dashboard access, optional verification, invalid/duplicate email, name/password boundaries, confirmation mismatch, cancellation/non-interactive refusal, active/unavailable Admin refusal, protected fields, unchanged participants and post-insert rollback. Test-only subclasses simulate terminal availability so hidden prompts can be answered without a physical terminal; production never has that override.

`php tests/MySql/bootstrap.php` is opt-in and reuses the guarded [MySQL harness](mysql-verification.md). Run `tests/MySql/setup.ps1` first and `cleanup.ps1` afterward, never against application data. The test requires empty fixture users, runs additive migrations on the marked disposable database, and starts separate workers with independent connections. A parent holds the same advisory lock; file barriers synchronize readiness, and `performance_schema.metadata_locks` must show **two PENDING named-lock requests** before release. All three rounds produced one Admin and one refusal, with hashing/login, optional verification, untouched participant snapshots, no domain events and released locks checked. This is genuine parallel MySQL contention, not a timing-only sleep or SQLite simulation. Only synthetic `.test` accounts are used; their credentials are in test code, never CLI arguments or real accounts.

No real application account was created or changed. Physical hidden-input rendering on a person's Windows terminal, browser login appearance and hosting console behavior remain deferred to final environment/manual review. The command is first-account setup, not a recovery backdoor or supported way to add later Admins. Existing Admins use normal password recovery; later Admin provisioning/recovery escalation remains a separate authorized operational process.
